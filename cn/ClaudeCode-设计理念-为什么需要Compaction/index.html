为什么需要 Compaction（上下文压缩）

Posted by zhangqinzhong on 2026-05-31
Estimated Reading Time 3 Minutes
Words 1k In Total
Viewed Times

问题

Claude 的上下文窗口是有限的（最大 1M token，但实际使用中几十万就很常见）。当对话历史积累到接近上限时，CC 会自动触发压缩（Compaction）。

为什么不直接截断（删掉最早的消息）？为什么需要如此复杂的压缩机制？

截断的致命问题

如果截断丢掉消息 1-2：

  • Claude 不知道用 Jest
  • 会去猜测测试框架，可能写错误的命令
  • 用户需要重新解释项目背景

截断破坏了对话的连续性，让 Claude 忘记了之前建立的所有共识和上下文。

Compaction 的核心思想：保留语义，压缩体积

压缩后：Claude 知道发生了什么（通过摘要），也能看到最新状态（通过保留的最近消息）。

为什么不只保留最近 N 条消息

"保留最近 20 条消息"是一种做法，但有问题：

重要的约束信息可能在很早的消息里，简单截断会丢失这些约束。

CC 的压缩方案是让 Claude 自己做摘要——它能识别哪些信息是"重要的长期约束"，哪些是"可以丢弃的中间步骤"。

四层压缩机制的分层原因

为什么不直接跳到最重的压缩？

代价递增

层次 触发阈值 成本 信息损失
snip 工具结果太大 近零（本地截断） 工具结果部分细节
microcompact 周期性 低（本地摘要化） 工具结果
autocompact ~95% 上限 高（API 调用） 早期对话细节

先用轻量方案，能解决问题就不升级到重量方案。只有真正无法通过轻量方案解决时，才触发花费额外 API 调用的 autocompact。

压缩后的缓存问题

autocompact 会破坏 Prompt Cache——压缩前的消息历史是缓存的基础，压缩后整个缓存需要重建。

这是 autocompact 的额外成本，也是 CC 不轻易触发它的原因。

压缩边界（compact_boundary）的作用

压缩后，旧消息不是"被删除"，而是从内存中释放（GC），但磁盘上保留完整历史。

/resume 命令恢复会话时，从 compact_boundary 处读取，不读取边界之前的内容——这样恢复速度快，同时保留了完整的审计历史。

用户体验层面的设计

压缩对用户几乎透明——他们看到一个短暂的"正在压缩历史"提示，然后对话继续。

没有 Compaction，用户会遭遇：

  • "上下文太长了"错误
  • 被迫开始新会话，丢失所有上下文
  • 对话质量随时间下降（因为 Claude 开始"忘记"早期内容）
