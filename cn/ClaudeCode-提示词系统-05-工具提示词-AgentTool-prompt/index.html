概述

AgentTool 的提示词是所有工具中最复杂的之一（287 行），定义了子 Agent 的调用时机、Agent 类型列表、Fork 模式语义、以及针对不同角色（协调者/普通 Agent/Teammate）的特定规则。

提示词的动态性

AgentTool 的提示词高度动态，根据多个条件生成不同版本：

影响输出的条件：

  • 是否启用 Fork 模式（isForkSubagentEnabled()）
  • 是否是协调者（isCoordinator）
  • 是否是 Teammate（isTeammate()）
  • 是否限制了可用 Agent 类型（allowedAgentTypes）
  • Agent 列表是否使用 attachment 注入（shouldInjectAgentListInMessages()）

核心内容

标准模式（无 Fork）

Fork 模式（isForkSubagentEnabled() 为 true）

Fork 的核心特性：

  1. 子 Agent 的工具输出不进入主线程上下文
  2. 主线程可以继续对话，不被阻塞
  3. Fork 内的 Agent 不能再次 Fork（防止无限递归）

Agent 列表注入方式

Agent 列表有两种注入方式（由 feature flag 控制）：

方式一：内嵌在工具描述中（默认）

Agent 列表直接写在 getPrompt() 的返回字符串里：

问题： Agent 列表包含 MCP 工具信息，每次 MCP 服务器连接/断开都会更新，导致工具 schema 缓存失效，约占 fleet 总 cache_creation token 的 10.2%。

方式二：通过 attachment 注入（shouldInjectAgentListInMessages() 为 true）

工具描述本身变为静态可缓存内容，Agent 列表作为消息附件独立管理。

加载逻辑

  • 来源文件：tools/AgentTool/prompt.ts · getPrompt()
  • 调用时机：每次组装工具列表时（或 attachment delta 触发时）
  • 完全动态：几乎没有可以全局缓存的静态内容
  • 缓存影响：Agent 列表的动态性是系统中最大的缓存命中率损耗来源之一，是 shouldInjectAgentListInMessages 优化的主要动机

依赖关系与互动

  • 与会话特定指引互动：系统层的"使用 AgentTool 的时机"在 getSessionSpecificGuidanceSection() 里有高层描述，AgentTool prompt 提供了具体的 Agent 类型列表和调用格式
  • 与 Fork 子 Agent 系统互动：Fork 模式的语义（后台运行、上下文隔离、不能再次 Fork）在这里声明，AgentTool.call() 里的 Fork 实现与这里的描述完全对应
  • 与 Prompt Cache 互动：Agent 列表的 attachment 化是 Prompt Cache 优化的一个典型案例，可以对比两种方式的缓存命中率差异
  • 与 Coordinator 系统互动：coordinator/coordinatorMode.ts（feature flag COORDINATOR_MODE）激活时，AgentTool 会收到 isCoordinator=true 参数，生成协调者专属提示词
  • 与 Team/Teammate 系统互动：SendMessageTool、TaskCreateTool 等工具的存在使多 Agent 协作成为可能，AgentTool prompt 里的 Teammate 约束确保成员 Agent 正确融入团队工作流
