Flutter GenUI 与 A2UI 协议：让 Agent 直接操作 UI 的工程闭环

现在大部分 AI 应用的交互模式还是聊天框。Agent 输出一段 Markdown，用户看完再打字追问，来来回回。但有些场景——选航班、填表单、筛商品、做审批——点两下按钮比打五行字快得多。

这就是 A2UI 和 Flutter GenUI 要解决的问题。

A2UI 是什么

A2UI（Agent-to-User Interface）是 Google 开源的一套协议，2025 年底公开，Apache 2.0 许可证。核心思想一句话：

Agent 不生成可执行代码，而是生成声明式 JSON 描述，客户端用自己的原生组件渲染。

JSON 里写的是"这里需要一个日期选择器、一个按钮、一个列表"，而不是 <script> 标签或 React 组件。客户端拿到这些描述后，从自己的组件目录（Catalog）里找对应的 Widget 渲染。

这样做的好处：

  • 安全：Agent 输出的 JSON 不是代码，不会被执行。客户端只渲染自己认识的组件
  • 跨平台：同一份 JSON 描述，Flutter 渲染成 Material、Lit 渲染成 Web Component、Angular 渲染成自己的模板
  • 品牌可控：渲染用的是你自己的设计系统，不会出现千篇一律的 AI 风界面
  • 可增量更新：协议支持流式推送组件树变更，UI 可以随着对话进行逐步展开

A2UI 有四种核心消息类型：createSurface（创建渲染面）、updateComponents（更新组件树）、updateDataModel（更新数据）、deleteSurface（销毁面），全部走 JSON，支持流式传输。

目前协议版本是 v0.9.1，v1.0 候选版也在推进中。渲染器覆盖：Lit（Web Component）、Angular、Flutter GenUI、React。SwiftUI 和 Jetpack Compose 在计划中。

Flutter GenUI：Flutter 侧的落地

GenUI 是 Flutter 团队基于 A2UI 协议做的 SDK。它在 A2UI 之上加了一层编排逻辑，协调用户、Widget、Agent 三者的信息流。

核心对象：

  • Catalog — 暴露给 Agent 的组件清单。每个条目包括组件名、字段 Schema、Widget Builder。Agent 只能调用 Catalog 里声明的组件，不能凭空创造
  • DataModel — 可观察的 UI 状态仓库，数据变化自动驱动 Widget 更新
  • A2uiTransportAdapter — 解析 LLM 文本流，从中拆分出 A2UI 消息块
  • SurfaceController / Surface — 管理生成 UI 的生命周期与渲染位置
  • Conversation — 高层封装，把 Transport 和 Controller 打包成一组简洁的 API

与传统文本 Chatbot 的区别

以攀岩 App 为例对比两种模式：

传统版：用户问"帮我找个适合初学者的攀岩路线"，Agent 返回大段 Markdown 列表。用户筛选条件要说"再帮我按难度排一下"，又一轮文本往返。

GenUI 版：Agent 直接要求客户端生成一组 Card 和 Filter Chip。用户点按钮筛选，触发的事件携带"当前 Surface、组件 ID、选项值"回传给 Agent。Agent 理解这是筛选操作，更新列表组件。

关键区别：Agent 不需要返回所有的数据，只需要返回"这里应该有一个 RecipeSelector，数据标识符是 xyz"。客户端从本地数据源按标识符拉取真实数据，用自己的预制 Widget 渲染。

前端新增的工程成本

GenUI 把复杂度从"写 Prompt"转移到了"定义 UI Contract"。前端需要补：

1. 组件 Catalog 设计。 明确 Agent 可调用的组件清单、字段命名、必填项、触发事件。不要让 Agent 把按钮嵌在卡片嵌在列表里叠出诡异组合。

2. Schema 设计。 类似 API 设计——太松 Agent 乱填，太死限制组合能力。每个组件需要定义字段类型、默认值、校验规则。

3. 事件设计。 用户操作时，事件需要携带 Surface ID、组件来源、业务上下文快照。Agent 收到的不是单纯的 “button clicked”，而是"在 booking 这个 Surface 上，confirm 按钮被点了，当前表单数据是 {datetime: …, guests: 3}"。

4. Fallback 容错。 Agent 可能生成非法 JSON、引用不存在的组件、网络中断。客户端需要有降级路径，回到文本模式或普通表单。

适用场景与边界

适合（文本来回解释太累，UI 操作更直接）：

  • 电商筛选——动态生成价格/品牌条件卡片
  • 旅行规划——可编辑行程表单
  • 企业审批——审批卡片 + 确认/驳回按钮
  • 教育 App——自适应学习界面组合

共性：用户需要不断输入约束、确认结果、调整参数。

不适合：

  • 判断/决策密集型任务。Agent 可能选错组件、给错默认值
  • 核心交易流。建议还是传统确定型 UI + 人工校验
  • 协议未稳定场景。A2UI 仍在快速迭代，v0.8 到 v0.9 有不兼容变更

实践建议

从窄场景切：找一个"文本墙影响体验"的 AI 功能，抽取 5-10 个稳定组件，定义 Catalog/Schema/事件上下文，让 Agent 在小范围内生成 UI，观察任务完成率是否提升。

长远看，AI 应用界面会从"聊天框挂应用"演变为"应用原生预留可组合、可验证的 Agent 操作空间"。Flutter GenUI 和 A2UI 是往这个方向走的重要一步。

一句话：GenUI 不是让模型直接画界面，而是构建 “Agent 意图 → JSON 描述 → 客户端可信组件 → 用户操作 → Agent 回传” 的闭环。控件、状态、事件、权限都在客户端可控循环内，这比"让 AI 生成 React 代码然后提心吊胆"安全得多。
