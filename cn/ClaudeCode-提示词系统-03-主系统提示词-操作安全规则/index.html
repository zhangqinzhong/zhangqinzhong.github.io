操作安全规则

Posted by zhangqinzhong on 2026-06-28
Estimated Reading Time 6 Minutes
Words 1.4k In Total
Viewed Times

概述

定义 Claude 在执行有影响力的操作时的决策框架：什么时候直接做，什么时候先问用户。核心逻辑是”根据操作的可逆性和影响范围决定是否确认“。

逐段解读

决策框架：可逆性 × 影响范围

这两个维度是决策的核心：

可逆 不可逆
本地影响 ✅ 直接做（编辑文件、跑测试） ⚠️ 确认（rm -rf、git reset —hard）
影响他人 ⚠️ 确认（push 代码） ❌ 强烈确认（force push、删分支）

“blast radius”（爆炸半径） — 借用运维术语，指操作出错后受影响的范围。一个修改本地文件的操作 blast radius 很小；一次 force push 到主分支的操作 blast radius 极大。

授权不可继承

这条规则解决了一个微妙但重要的问题：用户在某个上下文批准了某个操作，不代表这个批准在所有情况下都有效。

反例：用户说”帮我 push 一下功能分支”，Claude 成功了。之后用户说”帮我修个 bug”，Claude 不能因为之前有过 push 的批准，就在修 bug 后自动 push。

高风险操作列表

规定了四类需要确认的场景：

  1. 破坏性操作：rm -rf、删分支、覆盖未提交更改
  2. 难以撤销的操作：force push、git reset --hard、修改已发布 commit
  3. 影响他人可见的操作：push 代码、创建/评论 PR、发送消息到 Slack/邮件
  4. 上传到第三方服务：图表工具、pastebin——即使后来删除也可能被缓存

遇到障碍不走捷径

这条规则针对一个常见的”懒人做法”：当遇到 pre-commit hook 失败、lock 文件占用、merge conflict 等问题时，最简单的办法往往是绕过检查或强制删除。Claude 被明确禁止这样做——应该先理解问题，再针对性解决。

具体例子：

  • lock 文件：先查是哪个进程持有，而不是直接删
  • merge conflict：解决冲突，而不是丢弃变更
  • pre-commit hook 失败：修复根本原因，而不是 --no-verify

应用场景

Claude 直接执行（无需确认）：

  • 编辑文件
  • 运行测试、lint
  • 读取文件、搜索代码
  • 创建新文件（非系统级）
  • 本地 git add / commit（不含 push）

Claude 会先确认：

  • git push（尤其是 force push）
  • 删除文件/目录
  • 数据库操作（drop、truncate）
  • 发送消息到 Slack/邮件
  • 修改 CI/CD 配置
  • 调用会发送数据到外部服务的 API

加载逻辑

  • 位置：系统提示词静态层第四块
  • 缓存：全局缓存
  • 条件：始终加载（CLAUDE_CODE_SIMPLE 下也会加载，是极少数例外）
  • 可被覆盖：用户在 CLAUDE.md 中写明”无需确认直接执行”，或当前权限模式为 bypassPermissions，Claude 可以更自主地行动，但仍需关注风险

依赖关系与互动

  • 与权限系统互动：这段 prompt 定义了 Claude 的主观判断层，权限系统（hooks/toolPermission/）是机械检查层。两者互补：权限系统负责 allow/deny 规则匹配，本规则负责 Claude 在规则允许时的主动决策
  • 与 BashTool 权限互动：checkPermissions() 的 isReadOnly() 判断与这里的”可逆性”概念直接对应——只读操作 = 可逆 = 自动允许
  • 与 CLAUDE.md 互动：CLAUDE.md 中写入的永久指令可以改变这里的默认行为（比如”对这个仓库始终 push”）
  • 与任务执行规范互动：任务规范控制”做多少”，本规则控制”做之前是否确认”

设计亮点

“measure twice, cut once”（量两次，切一次）作为结尾，是木工谚语，在工程领域被广泛引用，表达”操作前多想一步”的工程直觉，比技术语言更直观。
