角色定义

概述

系统提示词的第一块，定义 Claude 是谁、做什么、有什么底线限制。这是整个提示词系统的"总纲"，后续所有规则都建立在这个基础上。

完整原文

注：当用户配置了自定义 Output Style 时，第一句话会变为：
"You are an interactive agent that helps users according to your 'Output Style' below, which describes how you should respond to user queries."

逐段解读

第一句：身份声明

“interactive agent” — 强调这是一个代理，不是问答机器人。它会主动使用工具、执行操作、完成任务，而不仅仅是回答问题。

“software engineering tasks” — 明确主要场景是软件工程。这个定位影响后续所有行为：当指令模糊时，优先按编程任务理解（例如用户说"帮我改 methodName"，Claude 应该去代码里找这个方法并修改，而不是简单回答"改成 snake_case 是 method_name"）。

第二段：安全边界

这段是安全政策的核心声明，定义了一条清晰的边界：

允许 拒绝
CTF 挑战 DoS 攻击
授权渗透测试 大规模目标攻击
防御性安全研究 供应链污染
安全教育 恶意目的的检测规避

对于双用途工具（C2 框架、凭据测试、漏洞利用开发），要求提供明确的授权上下文才能协助。这避免了简单的"允许/拒绝"二元判断，改为基于上下文的判断。

第三段：URL 限制

防止 Claude 编造不存在的链接，这种情况在编程助手场景中很常见（比如生成假的文档链接、NPM 包链接等）。唯一例外是用户自己提供的 URL，或者 Claude 高度确信与编程相关的 URL。

应用场景

  • 每次 API 调用都会包含这段文字，它是系统提示词的开头，影响 Claude 对所有后续指令的解读框架
  • 当用户提出边界模糊的安全相关请求时（如"帮我写一个端口扫描器"），Claude 会在这个框架下判断是否需要确认授权
  • 当 Claude 想引用外部资源但不确定 URL 是否真实存在时，会主动告知用户无法提供链接

加载逻辑

  • 位置：系统提示词第一块，静态层最前端
  • 缓存：全局缓存（scope: 'global'），所有用户共享
  • 条件：
    • 设置 CLAUDE_CODE_SIMPLE=1 时，整个角色定义被替换为三行简版
    • 配置了 Output Style 时，第一句话会被替换
    • Proactive 模式（KAIROS）下，整个静态层被替换为自主 Agent 提示词

依赖关系与互动

  • 被依赖：所有后续规则（任务执行规范、操作安全规则等）都建立在这个身份定义上
  • 与 Output Style 互动：getOutputStyleSection() 配置会修改角色定义的第一句话，控制 Claude 的整体输出风格
  • 与 getSimpleDoingTasksSection() 互动：“software engineering tasks” 的定位在任务规范章节有具体细化，包括如何对待模糊指令、如何控制代码修改范围

设计亮点

“interactive agent” 而不是 “assistant”
这个措辞选择是刻意的。“assistant” 暗示被动响应，“agent” 暗示主动执行。这一字之差会影响模型的行为倾向——当用户说"帮我修这个 bug"，agent 会主动去读代码、找 bug、修改、验证，而 assistant 可能只是给出修改建议。

安全边界的条件式设计
不是简单的"禁止安全工具"，而是"双用途工具需要授权上下文"。这样既保留了安全从业者的合法需求，又防止了恶意使用。
