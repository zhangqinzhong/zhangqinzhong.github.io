为什么 AbortController 要用 WeakRef

Posted by zhangqinzhong on 2026-05-31
Estimated Reading Time 2 Minutes
Words 668 In Total
Viewed Times

背景

CC 中到处使用 AbortController 来取消异步操作——中断 API 请求、停止工具执行、终止子 Agent。当一个父操作需要中止所有子操作时，会创建"子 AbortController"，父中止时所有子也被中止。

朴素实现的问题

内存泄漏问题：

只要父 AbortController 存在，handler 就存在，handler 引用 child，child 就不能被 GC。即使调用方已经丢弃了 child，父还持有它的引用。

在 CC 这种大量创建子 Agent、工具调用、fork 的场景，泄漏会累积。

WeakRef 解决方案

内存安全矩阵

情况 行为
父中止，子还活着 子被中止 ✅
父中止，子已 GC WeakRef.deref() 返回 undefined，跳过 ✅
子中止（任何原因），父还活着 从父移除 handler，防止死 handler 堆积 ✅
子被 GC（未中止），父还活着 父 handler 变成死 WeakRef，下次父中止时跳过 ✅

{ once: true } 的重要性

once: true 确保：

  1. 父中止后 handler 自动被移除（不重复触发）
  2. 父中止后无法再中止第二次（AbortController 是一次性的）

maxListeners 的设置

Node.js 默认 EventEmitter 最多 10 个监听器，超过会警告。CC 中一个父 AbortController 可能有许多子操作（并行工具、swarm 中的所有队友），需要更高的限制。

模块级函数避免闭包

原因：闭包每次调用都分配一个新函数对象。模块级函数只有一个实例，通过 bind 传递参数，大量创建 AbortController 时节省内存。
