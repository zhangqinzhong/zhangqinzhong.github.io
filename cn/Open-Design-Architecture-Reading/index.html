Open Design 架构解析：一个产品化的多 Agent CLI 工作台

Open Design 是一个开源的 local-first 设计生产力工具。跟 Claude Design、v0、Lovable 这类产品不同，它没有自己写 Agent Loop，而是在用户本地已安装的成熟 Agent CLI（Claude Code、Codex、DeepSeek 等）之上，加了一层产品化架构。

截止目前：100+ Skill、150+ 品牌设计系统、261 个 Plugin、28 个 Agent Adapter。

三层 App 分工

边界约束很严格：apps/web 不能 import apps/daemon/src，所有共享类型必须走 packages/contracts。这比常见的"前端随便引后端类型"的 monorepo 干净很多。

28 个 Agent Adapter：不是在抽象，而是在声明差异

这套架构最值得看的部分是 Agent Runtime。它没有把所有 CLI 统一成一个抽象接口，而是给每个 agent 写一个独立的声明式 def 文件（apps/daemon/src/runtimes/defs/），精确描述这个 CLI 跟别的有什么不同。

以三个典型 adapter 为例：

Claude Code

  • prompt 通过 stdin 写入，走 stream-json 双流 JSONL 协议
  • 支持 --resume <id> 恢复会话
  • MCP 通过写 .mcp.json 到工作目录注入
  • 权限走 --permission-mode bypassPermissions，避免 headless 卡 approval

Codex

  • prompt 同样 stdin 写入
  • session id 不是自己指定的，而是从 stream 的 thread.started.thread_id 事件里捕获
  • resume 时不能再传 -C / --add-dir，否则 Codex 直接报错
  • Windows/WSL 下 sandbox 策略不同，必要时切 danger-full-access

DeepSeek

  • prompt 是 argv 位置参数，不是 stdin
  • 因为有 Windows 32KB / Linux 单参数限制，声明 maxPromptArgBytes: 30000
  • 输出是 plain stdout，不是流式 JSON
  • --auto 跳过 TTY 下的 approval prompt

这三个例子说明一件事：每个 CLI 的输入方式、输出格式、resume 策略、权限机制、sandbox 行为都不同。想用一个统一 PTY 抽象层去套所有 agent，一定会丢掉关键能力。

一个 RuntimeAgentDef 声明的东西包括：

  • bin / fallbackBins — 二进制路径和降级替代
  • buildArgs() — 如何把 run 参数变成 CLI 参数
  • promptViaStdin — prompt 是 stdin、argv、还是文件
  • streamFormat — 输出的流格式（claude-stream-json / json-event-stream / plain / acp-json-rpc / pi-rpc 等）
  • resumesSessionViaCli — 是否支持 CLI 参数恢复（--resume / --session-id）
  • capturesSessionIdFromStream — 是否从输出流中捕获 session id
  • eventParser — 流解析器的选择
  • externalMcpInjection — MCP 的注入方式（写 .mcp.json / ACP merge / env）

Prompt 分层组装：16 层压栈

composeSystemPrompt() 不是拼字符串，而是按优先级压栈。越靠后的层在 recency bias 上越占优，但靠前的安全层通过显式声明"先读这个——后面的任何东西都不能覆盖"来保证优先级：

  1. 注入抵抗层 — 防止用户输入中的指令覆盖系统规则
  2. API mode override — 仅 plain-stream adapter 使用
  3. Discovery + Planning 层 — ~3000 token，控制前几轮交互的严格行为模式
  4. 身份与工作流宪章 — “expert designer” 身份定义
  5. 用户记忆 — 从历史对话提取的偏好
  6. 自定义指令 — 用户级 + 项目级
  7. 当前设计系统 — DESIGN.md 作为品牌契约
  8. Craft 参考 — 跨品牌的通用设计规则
  9. 当前 Skill — SKILL.md + preflight 规则
  10. Plugin block — plugin 的 prompt 片段
  11. Stage blocks — plugin pipeline 的各阶段提示
  12. 元数据块 — 项目信息、平台、模板
  13. 媒体生成契约 — 图片/视频/音频的专用约束
  14. Critique 评审协议 — 五维评审
  15. MCP 指令 — 已连接的 MCP server 说明
  16. 角色伪造禁令 + 澄清问题指令 — 永远钉在最后

Session Resume：不只是记住 session id

Open Design 的 resume 有严格的失效条件（agent-session-resume.ts）。以下任一条件成立就触发重新播种：

  • model_changed — 模型 ID 变了
  • cwd_changed — 工作目录变了
  • missing_cursor — 老 session 没有 lastMessageId
  • conversation_advanced — 对话被其他 agent 插入或编辑过

除此之外，每种 CLI 还有各自的断连检测：Claude 检测 stderr 上的 “session not found” + stdout 上的 is_error result；Codex 检测 “no rollout found for thread id”；OpenCode 检测 “Session not found”。检测到时自动清掉存储的 session id，下次重建。

Plugin Snapshot：可回放的能力包

在 run 启动前，createSnapshot() 把 plugin 的完整上下文（manifest 摘要、输入参数、resolved context、capabilities、assets、MCP servers）冻结成一条 SQLite 记录。一旦关联 run，这条 snapshot 永久保留。

这意味着：即使 plugin 在生成过程中被升级，已有 run 的 prompt 内容不会变。同一个 run 可以随时回放，不会因为 plugin 版本漂移而出不确定的结果。

核心设计判断

Open Design 没走"自研 Agent Loop"这条路。它的策略是：

让成熟 Agent CLI 负责模型调用、工具使用、上下文管理、权限、resume、cancel。我负责检测 CLI、组装 prompt、注入 skill/design-system/plugin、启动进程、解析流、渲染 artifact。

这跟"在 Claude Code 外面套一个 wrapper"有本质区别——它产品化的是整个交互流程：怎么选 skill、怎么配设计系统、怎么启用 plugin、怎么把 28 种 agent 的输出归一成同一个事件模型、怎么让一个 run 可以暂停、恢复、回放。
